## 1. Resumen ejecutivo

### Gap que resolvió T1.3

Antes de T1.3, el webhook de Stripe (configurado en Stripe Dashboard
apuntando a la landing) llegaba a `https://www.usadona.com/api/webhook`,
donde el landing **solamente** verificaba la firma y enviaba el welcome
WhatsApp. **No** contactaba al backend, así que las suscripciones que
los usuarios pagaban en Stripe nunca se reflejaban en la base de datos
del backend ni acreditaban créditos al teléfono. El usuario veía
"saldo: 0" después de pagar.

### Estado final

- **Premium ($20/mes → 100 créditos)**: validado end-to-end con compra
  real. Saldo del usuario pasó de **70 → 170** créditos confirmando
  acreditación correcta.
- Stripe Webhooks dashboard muestra el endpoint
  `https://www.usadona.com/api/webhook` activo, con
  `checkout.session.completed` entregado en HTTP 200 OK.
- Páginas legales `/soporte`, `/politica-de-privacidad` y
  `/terminos-y-condiciones` configuradas en Stripe.
- **Pro ($40/mes → 500 créditos)**: implementado y testeado en suite,
  pendiente de prueba real con compra.

## 4. Seguridad

### Secretos y variables

| Variable                  | Función                                            | Donde |
|---------------------------|----------------------------------------------------|---|
| `STRIPE_WEBHOOK_SECRET`   | Verificación de firma de Stripe en el landing      | Vercel + Render (legacy `/webhook/stripe`) |
| `INTERNAL_BRIDGE_SECRET`  | HMAC compartido entre landing y backend            | Vercel + Render (mismo valor) |
| `STRIPE_CREDITOS_PREMIUM` | Créditos a acreditar por plan Premium              | Render |
| `STRIPE_CREDITOS_PRO`     | Créditos a acreditar por plan Pro                  | Render |
| `BACKEND_URL`             | URL del backend para el bridge                     | Vercel |

### Validación criptográfica

- **Stripe → Landing**: `stripe.webhooks.constructEvent()` valida
  firma con `STRIPE_WEBHOOK_SECRET` (esquema oficial de Stripe sobre
  body crudo, tolerancia de timestamp).
- **Landing → Backend**: HMAC-SHA256 sobre el body JSON exacto que se
  envía. Header `X-Internal-Signature: <hex digest>`. En el backend:
  `hmac.compare_digest(esperado, sig_header)` (resistente a timing
  attacks).
- **Fail-fast al import**: tanto `agent.billing` (STRIPE_WEBHOOK_SECRET)
  como `agent.main` (INTERNAL_BRIDGE_SECRET) levantan `RuntimeError`
  al cargar el módulo si las variables faltan en producción. El
  deploy aborta antes de servir tráfico.

### Idempotencia (3 niveles)

| Nivel | Llave                                         | Tabla                          |
|-------|-----------------------------------------------|--------------------------------|
| 1     | `event.id`                                    | `evento_stripe_procesado`      |
| 2     | `invoice.id` (solo `invoice.payment_succeeded`)| `suscripcion_stripe.ultimo_invoice_acreditado` |
| 3     | `stripe_session_id` (= invoice_id)            | `transacciones_credito`        |

Cualquier reentrega de Stripe (que es habitual por diseño) es
absorbida sin duplicar créditos. Triple defensa para resistir tanto
event.id distintos con mismo invoice como duplicados exactos.

### No secretos en repo

- `.env.example` documenta nombres y descripciones; nunca valores.
- Las variables se configuraron directamente en Render y Vercel.
- Ningún PR de T1.3 contiene literales de secret.
- El reporte de implementación de cada PR fue redactado sin filtrar
  los valores reales.

## 8. Riesgos pendientes y monitoreo recomendado (24–48h)

### Monitoreo activo

1. **Stripe Webhooks Dashboard** (Settings → Developers → Webhooks):
   Vigilar el endpoint `https://www.usadona.com/api/webhook`. Cualquier
   evento con status distinto a 200 (especialmente 500 sostenidos) es
   señal de alerta. Stripe marca endpoints como `Failing` tras múltiples
   fallos consecutivos.

2. **Vercel logs del landing**: filtrar por `[BRIDGE]` o
   `bridge_failed`. Indica que el bridge intentó alcanzar el backend
   y falló (timeout, 401 desincronizado, 500 del backend).

3. **Render logs del backend**: filtrar por
   `/internal/stripe-event`. Vigilar:
   - `signature_invalid` (401): secret desincronizado o ataque.
   - `processing_error` (500): excepción inesperada en
     `procesar_evento_suscripcion`.
   - `subscription_no_persistida_retry` (500): race transitorio
     normal entre invoice y checkout. **Esperar autoresolverse en el
     siguiente reintento de Stripe.**

### Riesgos abiertos conocidos

| Riesgo | Severidad | Mitigación / Plan |
|---|---|---|
| Welcome WhatsApp duplicado si bridge falla y Stripe reintenta | Bajo | El usuario recibe a lo sumo 2-3 welcomes en minutos. Aceptable. |
| Pro +500 sin probar con compra real | Medio | Programar prueba con $40 (puede ser real o Stripe test mode con price equivalente). |
| `invoice.payment_succeeded` de renovación no observado | Medio | Ocurre en el segundo periodo (~30 días). Vigilar Render logs cuando se acerque. |
| Página `/soporte` apunta a `hola@usadona.com` | Bajo | Confirmar que ese inbox está monitoreado para temas de soporte; si no, configurar `soporte@usadona.com`. |
| `creditos_mensuales` es snapshot al crear | Info | Si el owner cambia `STRIPE_CREDITOS_*` en Render, suscripciones existentes mantienen el valor original. Por diseño. |
