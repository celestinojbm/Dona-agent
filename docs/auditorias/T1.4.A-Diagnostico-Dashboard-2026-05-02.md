## 1. Cómo funciona hoy el dashboard

### Ruta y autenticación

- **`landing/app/dashboard/page.tsx`** — Server Component que llama
  `auth()` (NextAuth). Si no hay sesión, redirige a `/login`. Si la
  hay, monta `<DashboardClient session={session} />`.
- **`landing/auth.ts`** — NextAuth con provider `Credentials`
  (email + password). Su `authorize` lookups Stripe Customer por
  email y verifica que tenga una `subscription` con `status=active`.
  Si pasa, retorna `{id, email, stripeCustomerId, subscriptionId, plan: priceId}`.
- **`landing/app/login/page.tsx`** — Form con email/password que
  llama a `signIn("credentials", ...)`.

### UI actual (`dashboard-client.tsx`)

La pantalla muestra **dos secciones**:

1. **Suscripción**
   - Etiqueta hardcoded: `"Plan activo"`.
   - Nombre del plan: cliente compara `session.plan` (priceId) con
     `process.env.NEXT_PUBLIC_STRIPE_PRICE_PRO`. Si match → "Pro";
     si no → **siempre "Premium"** (no maneja "Free" ni "unknown").
   - Texto fijo: `"Suscripcion activa — se renueva mensualmente"`
     (sin fecha real ni próxima renovación).
   - Botón "Cancelar suscripcion" → `POST /api/cancel-subscription`.

2. **Conexiones**
   - Lista hardcoded de 3 items: Gmail, Google Calendar, WhatsApp.
   - `connected` está hardcoded: WhatsApp `true`, las otras `false`.
   - Botones "Conectar"/"Desconectar" sin handler — no hacen nada.

**No se muestran:** créditos disponibles, créditos mensuales del
plan, historial de transacciones, fecha de próxima renovación,
fecha de cancelación si aplica, número de teléfono vinculado.

### Cancel flow actual

`landing/app/api/cancel-subscription/route.ts`:
1. Toma `subscriptionId` de la sesión NextAuth.
2. Llama directo a `stripe.subscriptions.cancel(subscriptionId)`.
3. Retorna el status nuevo de Stripe.

**No notifica al backend.** El backend se entera vía webhook
(`customer.subscription.deleted` → `_procesar_subscription_deleted`
en T1.3.C) y marca `SuscripcionStripe.status='canceled'`. Hay un
delay (segundos a minutos) entre el clic y la actualización en DB.

### Funciones backend ya disponibles

- `agent.billing.obtener_saldo(telefono) → int` — saldo actual.
- `agent.billing.obtener_resumen(telefono) → dict` — saldo +

`obtener_resumen` cubre prácticamente todo lo que el dashboard
necesita en términos de créditos/historial. Solo falta que el
endpoint exponga la suscripción y que la fila de `SuscripcionStripe`

| Últimas transacciones | `transacciones_credito` (últimas 5) | **No mostrado** |
| Fecha próxima renovación | (NO está en DB) — se obtiene de Stripe `subscription.current_period_end` | No mostrado |

### Datos de Stripe que aún hay que pedir (no están en DB)

- **Próxima fecha de renovación** (`current_period_end`).
- **Fecha de cancelación si aplica** (`cancel_at_period_end`,
  `canceled_at`).
- **Método de pago** (last4 de tarjeta, marca).

Estos se pueden:
- (a) obtener desde el landing llamando Stripe directamente
  (NextAuth ya tiene `stripeCustomerId`), **o**
- (b) cachearlos en la fila `SuscripcionStripe` cada vez que llegue
  un evento (T1.3.C ya procesa `customer.subscription.updated` —
  agregar campos sería barato).

**Recomendación:** opción (a) para fechas (cambian seguido y son
baratas de fetchar). Opción (b) si hace falta mostrar histórico.

### Datos que están en frontend pero deberían venir de backend

- **Connections** (Gmail/Calendar/WhatsApp) — hoy hardcoded en el
  cliente, pero el backend tiene `UsuarioGoogleAuth` (telefono +
  tokens OAuth). Para mostrar correctamente "Conectado" hay que
  consultar.

## 4. Cómo identificar al usuario del dashboard

Este es **el punto más sensible** del diseño T1.4. Hoy:

| Identificador | Donde vive | Set por |
|---|---|---|
| `email` | `session.user.email` (NextAuth) | El usuario lo tipea en /login |
| `stripeCustomerId` | `session.stripeCustomerId` | NextAuth: lookup por email en Stripe |
| `subscriptionId` | `session.subscriptionId` | NextAuth: primera sub `active` del customer |
| `plan` (priceId) | `session.plan` | NextAuth: primer item de la sub |
| `telefono` | **NO está en la sesión** | — |

### El gap clave: email → telefono

El backend opera por `telefono`. La sesión solo tiene email. La
única tabla que une los dos es **`suscripcion_stripe`**:

```
session.email (Stripe customer.email)
    ↓ buscar Customer en Stripe por email
session.stripeCustomerId (cus_xxx)
    ↓ JOIN suscripcion_stripe.customer_id = cus_xxx
suscripcion_stripe.telefono
    ↓ usar como llave en saldo_creditos / transacciones_credito
saldo
```

### Recomendación de identificador para el endpoint

El endpoint backend de T1.4.B debe aceptar **`subscription_id`**
(no email ni teléfono) porque:

1. Es la PK natural de `SuscripcionStripe`. Lookup O(1).
2. La sesión NextAuth ya lo tiene (no requerimos round-trip extra).
3. No filtra el teléfono al cliente (el teléfono nunca cruza la red
   pública si no hace falta).
4. Si el atacante intenta forjar un `subscription_id` de otro
   usuario, falla la verificación HMAC del bridge interno (mismo
   patrón que T1.3.D); el endpoint solo devuelve datos al landing
   autenticado server-side.

## 5. Riesgos de seguridad

### 🔴 P0 (crítico) — Bug actual de auth

**`landing/auth.ts:13-48`**: la función `authorize` recibe email +
password, pero **el password nunca se valida**. Solo se chequea que
exista un Stripe Customer con ese email + suscripción activa. Bug
real, no hipotético: cualquier persona que conozca el email de un
usuario suscrito puede entrar a su dashboard, ver datos, y
**cancelar su suscripción**.

```ts
// auth.ts línea 13–25:
async authorize(credentials) {
  const email = credentials?.email as string | undefined;
  const password = credentials?.password as string | undefined;
  if (!email || !password) return null;
  // ⚠ password se valida con !password, pero NUNCA se compara
  //   contra un hash guardado. Sólo basta que sea no-vacío.
  const customers = await getStripe().customers.list({email, limit: 1});
  if (customers.data.length === 0) return null;
  // ...
}
```

**Bloqueador para T1.4.D:** mostrar saldo y permitir cancelación a
quien sea que conozca un email es inaceptable. **T1.4 debe corregir
auth antes de exponer datos.**

### 🟡 Otros riesgos

| Riesgo | Severidad | Mitigación |
|---|---|---|
| `/api/cancel-subscription` sin CSRF explícita (NextAuth solo cubre sus propios endpoints) | Media | Agregar `Origin` header check o CSRF token. NextAuth con `useSession` ya manda cookies SameSite. |
| Sin rate limiting en `/login` | Media | Brute force de emails de subscribers conocidos. Mitigación: rate limit por IP. |
| `subscription_id` filtrable si se loguea | Baja | No loguear ID en errores client-side; ya está OK en el código actual. |
| Backend admin endpoints requieren `ADMIN_TOKEN` (no se debe usar para dashboard) | OK | Diseñar T1.4.B con HMAC nuevo (`INTERNAL_BRIDGE_SECRET` o uno propio). NO reusar ADMIN_TOKEN. |

## 6. Propuesta de arquitectura mínima

### Diagrama del flujo propuesto

```
┌─────────────────────┐
│ Browser             │
│  GET /dashboard     │
└─────────────────────┘
          │ cookies (NextAuth JWT)
          ▼
┌─────────────────────────────────────────────────────────────┐
│ Vercel · landing                                            │
│                                                             │
│  /dashboard (server component)                              │
│   - auth() → session {email, stripeCustomerId,             │
│              subscriptionId, plan}                          │
│   - validar password (T1.4 auth fix antes de T1.4.D)       │
│                                                             │
│  /api/dashboard-data (server, T1.4.C)                      │
│   - auth() → tomar subscriptionId                          │
│   - llamar BACKEND_URL/internal/usuario-resumen con HMAC   │
│   - merge con datos Stripe (current_period_end, etc.)      │
│   - retornar JSON al cliente                                │
└─────────────────────────────────────────────────────────────┘
          │ POST con HMAC
          ▼
┌─────────────────────────────────────────────────────────────┐
│ Render · backend                                            │
│                                                             │
│  POST /internal/usuario-resumen (T1.4.B, HMAC required)    │
│   body: {subscription_id: "sub_xxx"}                        │
│   1. _verificar_firma_interna() (mismo patrón T1.3.D)      │
│   2. SELECT FROM suscripcion_stripe WHERE                  │
│      subscription_id = ?                                    │
│   3. SELECT FROM saldo_creditos WHERE telefono = ?         │
│   4. SELECT FROM transacciones_credito WHERE telefono = ?  │
│      ORDER BY creado DESC LIMIT 10                          │
│   5. Retornar JSON read-only:                               │
│      {                                                      │
│        plan_codigo, status, creditos_mensuales,            │
│        ultimo_invoice_acreditado,                           │
│        saldo, total_comprado, total_consumido,             │
│        ultimas_transacciones: [...]                        │
│      }                                                      │
└─────────────────────────────────────────────────────────────┘
```

### Decisiones de diseño

1. **`subscription_id` como llave del endpoint** — NO email ni
   teléfono. Es lo más estrecho que podemos pasar.
2. **HMAC reusa `INTERNAL_BRIDGE_SECRET`** — ya existe, ya está
   sincronizado en Vercel/Render, ya tiene el patrón de
   `_verificar_firma_interna` en `agent/main.py`. Reusar reduce
   superficie de configuración.
3. **Read-only** — el endpoint no muta nada, solo SELECTs. Ningún
   path puede mover dinero, créditos o suscripciones desde T1.4.B.
4. **Sin teléfono en la respuesta** — el dashboard no lo necesita
   mostrar, así que tampoco viaja por la red pública. El landing
   server-side es quien recibe el JSON; nunca cruza al browser.
5. **Cache local de Stripe data en el landing** — para `current_period_end`
   y método de pago, llamar Stripe SDK desde el server route, no
   desde el browser. Las claves Stripe nunca llegan al cliente.
6. **Cancelación**: opcionalmente cambiar de `cancel()` (immediate)
   a `update(cancel_at_period_end: true)` para que el usuario pueda
   usar lo que pagó. Decisión owner.
