## 2. Guardrails capturadas para T1.4.D

Estas reglas vienen de la revisión del owner sobre T1.4.C. Cuando se
inicie T1.4.D, **deben respetarse desde el primer commit**, no como
follow-up.

### 2.1 Identificador de usuario sólo desde la sesión server-side

**Regla:** `landing/app/api/dashboard-data/route.ts` (T1.4.D) **NO**
debe aceptar `subscription_id` desde el cliente/browser.

El identificador debe leerse **únicamente** desde la sesión server-side
de NextAuth, por ejemplo:

```ts
import { auth } from "@/auth";

export async function GET() {
  const session = await auth();
  if (!session) return new Response(null, { status: 401 });

  const subscriptionId = (session as any).subscriptionId;
  if (!subscriptionId) return new Response(null, { status: 403 });

  // ... POST a backend con HMAC, usando subscriptionId tomado de session
}
```

**Razón:** El HMAC protege la comunicación landing → backend contra
manipulación en tránsito, pero NO impide que un usuario autenticado
intente consultar la suscripción de OTRO usuario enviando un
`subscription_id` ajeno desde el navegador. Confiar en `session.*`
server-side es la única forma de garantizar que el dato pedido
corresponde al usuario logueado.

**Aplica también a:**
- `/api/cancel-subscription` (ya cumple — usa `session.subscriptionId`).
- Cualquier futuro proxy del landing al backend (T1.4.E, T1.4.F).
- Cualquier ruta que mande request firmado al `/internal/*` del backend.

### 2.2 No loguear `subscription_id` completo en producción

**Regla:** En producción, los identificadores Stripe (`sub_xxx`,
`cus_xxx`, `in_xxx`) se truncan o redactan en logs. No son secretos
crudos pero correlacionan trivialmente con un usuario específico una
vez combinados con otros datos.

**No es blocker para T1.4.C.** Aplica a código nuevo de T1.4.D en
adelante. Patrones aceptables:

```python
# Backend (Python):
sub_short = sub_id[:8] + "..." + sub_id[-4:] if len(sub_id) > 12 else sub_id
logger.info(f"[INTERNAL] usuario-resumen para sub={sub_short}")
```

```ts
// Landing (TypeScript):
const subShort = subId.length > 12
  ? `${subId.slice(0, 8)}...${subId.slice(-4)}`
  : subId;
console.log(`[BRIDGE] dashboard-data sub=${subShort}`);
```

El código existente de T1.3.* y T1.4.C ya quedó como está. No requiere
refactor inmediato.

## 3. Diseño tentativo de T1.4.D (sin implementar)

Para que cuando arranquemos no se pierda el contexto:

### Archivo nuevo

`landing/app/api/dashboard-data/route.ts` — handler `GET`.

### Flujo server-side

1. `const session = await auth();`
2. Si no hay sesión → `401 unauthenticated`.
3. Tomar `subscriptionId` de `session.subscriptionId` (NUNCA del request).
   Si no está → `403 no_subscription`.
4. Llamar al backend en paralelo a Stripe SDK:
   - **Backend** `POST {BACKEND_URL}/internal/usuario-resumen`:
     body `{"subscription_id": subscriptionId}` firmado con HMAC-SHA256
     reusando helper de `landing/lib/internal-bridge.ts` (extender el
     existente con `fetchUsuarioResumen(subscriptionId)`).
   - **Stripe SDK** `stripe.subscriptions.retrieve(subscriptionId)`:
     extraer `current_period_end` y `cancel_at_period_end`.
5. Mergear:
   - JSON del backend (saldo, plan, transacciones).
   - Datos de Stripe (current_period_end, cancel_at_period_end).
   - `email` desde `session.user.email`.
6. Retornar al cliente.

### Manejo de errores

| Backend respondió | Acción |
|---|---|
| 401 | Log "secret desincronizado" + 502 al cliente |
| 404 | 404 al cliente con mensaje "suscripción no encontrada en backend" |
| 500 | 502 al cliente, log para alerta |
| timeout | 504 al cliente |
| 200 OK | merge con Stripe data + 200 al cliente |

### Validación a correr en T1.4.D

- `npx tsc --noEmit` — 0 errores.
- `npm run lint` — sin nuevos.
- `npm run build` — pasa, ruta nueva registrada.
- Smoke manual: con sesión válida → 200 con datos.
- Smoke negativo: si la sesión no existe o no tiene
  `subscriptionId` → 401/403.

### Lo que NO hacer en T1.4.D

- No modificar el endpoint backend (T1.4.C ya está aprobado).
- No exponer `INTERNAL_BRIDGE_SECRET` ni `STRIPE_SECRET_KEY` al cliente.
- No aceptar `subscription_id` (ni cualquier otro id de usuario) del
  request del browser.
- No tocar UI del dashboard (eso es T1.4.E).
- No tocar cancelación (eso es T1.4.F).
