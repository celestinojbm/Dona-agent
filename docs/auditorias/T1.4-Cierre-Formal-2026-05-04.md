## 1. Resumen ejecutivo

### Gap que resolvió T1.4

Antes de T1.4, el dashboard de usuario (`/dashboard` en el landing) era
visualmente útil pero estaba desconectado de la realidad del backend:

- El plan se "deducía" de un priceId comparado con una env var pública.
- El estado de suscripción decía "Suscripcion activa — se renueva
  mensualmente" sin fecha real ni reflejo del backend.
- No había saldo, ni créditos mensuales, ni historial de transacciones.
- La autenticación recibía password pero **nunca lo validaba** —
  cualquiera con un email de subscriber podía entrar al dashboard
  ajeno y cancelar su suscripción.
- La cancelación era inmediata: el usuario perdía el acceso al
  instante aunque el ciclo ya estuviera pagado.

### Estado final

- **Dashboard muestra datos reales del backend Dona**: saldo (validado
  en producción: 170 créditos), créditos mensuales (+100 por
  renovación), Plan Premium activo, próxima renovación, movimientos
  recientes con razón / delta / fecha.
- **Auth segura**: password derivado HMAC del `customer_id` con
  `DASHBOARD_PASSWORD_SECRET`. Login rechaza si no coincide.
- **Cancelación coherente**: `cancel_at_period_end=true` preserva
  acceso y créditos hasta el final del período. UX visible
  ("Se cancela el DD/MM" + botón deshabilitado).
- **Estado fresco desde Stripe**: si el webhook al backend está
  retrasado, Stripe SDK es la fuente para `estado` y `puede_cancelar`.

### Detalle por sub-tarea

#### T1.4.A — Diagnóstico

Reporte read-only que identificó el bug P0 de auth, el gap de datos
en la UI, y propuso el plan A→F. No produjo código. Output:
`docs/auditorias/T1.4.A-Diagnostico-Dashboard-2026-05-02.md` y PDF.

#### T1.4.B — Fix P0 Auth Dashboard

```
password = "dona-" + hex(HMAC-SHA256(stripe_customer_id, DASHBOARD_PASSWORD_SECRET))[:12]
```

- Sin storage adicional. Determinístico. Único por usuario.
- Validación con `crypto.timingSafeEqual` antes del lookup de
  subscription, para no revelar si el customer existe.
- Fail-cerrado: sin `DASHBOARD_PASSWORD_SECRET`, todos los logins
  fallan (mejor bloquear que aceptar).
- CLI helper `landing/scripts/derive-dashboard-password.ts` para que
  el owner derive el password de un customer y lo entregue por canal
  seguro (WhatsApp via Dona).

#### T1.4.C — Backend `/internal/usuario-resumen`

- POST con HMAC reusando `INTERNAL_BRIDGE_SECRET` (mismo patrón que
  T1.3.D).
- Llave: `subscription_id`. PK natural de `SuscripcionStripe`,
  lookup O(1).
- Read-only: solo SELECTs. **Verificado** con test que cuenta filas
  antes/después.
- Códigos: 401 firma · 400 JSON · 404 sub no existe · 200 dato.
- Response: usuario · créditos · suscripcion · transacciones (hasta
  10) · resumen.
- 21 tests nuevos (suite total 575 verde).

#### T1.4.D — Landing `/api/dashboard-data`

- GET handler server-only. `subscriptionId` viene **solo** de
  `await auth()` (NextAuth session) — guardrail confirmado por Dona
  Control.
- Llama en paralelo a backend (`fetchUsuarioResumen` con HMAC) y a
  Stripe SDK (`subscriptions.retrieve` para `current_period_end` y
  `cancel_at_period_end`; en `stripe@22` el `current_period_end` vive
  en `items.data[0]`).
- Merge: backend + Stripe + email de sesión.
- **Follow-up T1.4.D**: Stripe es fuente más fresca para
  `estado_final` y `puede_cancelar`; `import "server-only"` en
  `internal-bridge.ts` para que un Client Component no pueda
  importarlo por error.

#### T1.4.E — UI dashboard con datos reales

- `dashboard-client.tsx` reescrito: 3 secciones (Créditos ·
  Suscripción · Movimientos) + skeleton + error card con retry.
- Diseño oscuro premium preservado (glass-card, fonts existentes).
- No expone teléfono ni IDs Stripe internos en UI.
- Tipos extraídos a `lib/dashboard-types.ts` (sin `server-only`)
  para reuso desde Client Components.

#### T1.4.F — Cancelación segura

- `subscriptions.cancel(id)` (immediate) → `subscriptions.update(id,
  {cancel_at_period_end: true})`.
- Backend (T1.3.C) ya preservaba el saldo en
  `customer.subscription.deleted`, así que el flow end-to-end es
  coherente.
- Respuesta extendida con `cancel_at_period_end`,
  `current_period_end` y `status` para que el dashboard refresque
  inmediatamente.

## 4. Seguridad y guardrails que quedaron

### Secretos / variables nuevas

| Variable | Función | Donde |
|---|---|---|
| `DASHBOARD_PASSWORD_SECRET` | Deriva passwords de dashboard por usuario | Vercel |

(Las demás variables —`INTERNAL_BRIDGE_SECRET`, `BACKEND_URL`,
`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_CREDITOS_*`—
ya existían post-T1.3.)

### Reglas vigentes (persistidas en memoria del agente)

1. **Server-side identifiers en proxy routes del landing**: rutas que
   van a `/internal/*` del backend toman IDs solo de `await auth()`
   (sesión NextAuth), nunca del request del cliente. Aplica a
   `/api/dashboard-data`, `/api/cancel-subscription` y cualquier
   proxy futuro. Confirmado por Dona Control durante T1.4.C/D.

2. **No loguear `subscription_id` completo en producción**: usar
   `subId.slice(0, 8) + "..." + subId.slice(-4)`. Aplica al código
   nuevo desde T1.4.D.

3. **`server-only` en módulos que tocan secretos**:
   `internal-bridge.ts` lleva `import "server-only"` para que el
   build falle si un Client Component lo importa por error.

### Tres niveles de defensa heredados de T1.3 + reforzados

- **HMAC** en `/internal/usuario-resumen` y `/internal/stripe-event`
  (mismo `INTERNAL_BRIDGE_SECRET`).
- **`compare_digest` / `timingSafeEqual`** en backend y landing.
- **Fail-cerrado** en producción si las env vars críticas faltan
  (lanza error al import de `agent.main`).

## 5. Riesgos pendientes / observaciones

| Riesgo | Severidad | Plan |
|---|---|---|
| Sin rate limiting en `/login` (brute force de emails) | Media | T1.5 |
| Sin rate limiting en `/api/dashboard-data` | Bajo | Sesión actúa como rate limit indirecto; T1.5 si se detecta abuso |
| Suprimida regla `react-hooks/set-state-in-effect` (Next 16) en `dashboard-client.tsx` | Info | Refactor a Suspense + `use(promise)` requiere Server Component; programar con bandwidth |
| Conexiones (Gmail / Calendar / WhatsApp) hardcoded en UI | Info | Out of scope T1.4; depende de OAuth real |
| Sin auto-refresh en dashboard | Bajo | Aceptable; el dashboard no es real-time |
| Cancelación pendiente no probada con compra real | Medio | Esperar primera cancelación voluntaria de un usuario o hacer test E2E con cuenta de prueba |
| `current_period_end=null` si Stripe rate-limita | Muy bajo | Dashboard maneja null y oculta la fecha |
| `DASHBOARD_PASSWORD_SECRET` filtrado → todos los passwords derivables | Alta | Rotar el secret invalida todos los passwords; comunicar a usuarios para recibir el nuevo |

## 6. Próximos pasos recomendados (post-T1.4)

### T1.5 — Dashboard polish + safety UX

- **Rate limiting** en `/login` (brute force) y `/api/dashboard-data`
  (sesión comprometida).
- **Aviso de cancelación pendiente** más visible (banner amber
  arriba, no solo dentro de la card).
- **Manejo de error coherente** cuando `DASHBOARD_PASSWORD_SECRET`
  no está configurada en dev (mensaje claro al desarrollador local).
- **Pequeñas mejoras de copy** en mensajes de error de carga.
- **Refactor del fetch a Suspense** (eliminar el suppression de
  `react-hooks/set-state-in-effect`) — opcional si bandwidth.

### T1.6 — Observabilidad mínima

- **Métricas en endpoint `/admin/metrics`** para contadores de
  `/internal/usuario-resumen` (200 / 401 / 404 / 500).
- **Logging estructurado** del bridge landing→backend con request
  id correlacionable.
- **Alerta** si el secret está desincronizado (Vercel y Render
  reportan distinto error rate de HMAC).

### T2.0 — Onboarding premium

- Tras compra Premium/Pro, **Dona envía proactivamente** el password
  derivado al usuario por WhatsApp (en vez de que el owner lo derive
  manualmente).
- Tour guiado del dashboard (saldo, plan, cancelación).
- **Email de bienvenida** desde dominio operativo (`hola@usadona.com`
  o equivalente verificado).
